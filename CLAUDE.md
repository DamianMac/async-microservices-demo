This is a demo application for showing how a microservice architecture can work using async messaging rather than http calls between services.

It's going to be based on .NET and Nimbus

## Layout

- `async-microservices.sln` - all .NET projects (.NET 9)
- `src/Services/` - backend API services (ASP.NET Core Web API, controllers)
  - `Catalog`, `Orders`, `Search`, `PaymentGateway`, `Email`, `Profile`
- `src/Enterprise/` - internal back-office apps (ASP.NET Core MVC)
  - `Warehouse`, `CatalogManager`
- Each .NET app has a sibling `{AppName}.Messages` class library (e.g. `src/Services/Catalog.Messages`) for its Nimbus message contracts. It references only `Nimbus.InfrastructureContracts`, and the app references it.
- `src/Shared/` - class library referenced by every .NET app, for cross-cutting bus plumbing (see Messaging observability)
- `src/client/` - demo storefront, Nuxt 4 SPA
- `infra/` - local dependencies via `docker-compose.yml` plus the `Caddyfile`
- `data/` - demo catalog for Nimbus Coffee Co. (`products.json`), product images (`images/*.svg`, PNGs in `images/rendered/`), and the scripts that generate and render them (see README)
- `docs/` - `architecture.svg`, the system diagram, generated by `generate-architecture.py` (edit the script, not the SVG), shown in `docs/README.md`, plus a simpler slide version (`architecture-slide.svg`/`.png`, from `generate-architecture-slide.py`) and the order saga as swimlanes (`saga-slide.svg`/`.png`, from `generate-saga-slide.py`). Update it when services or messages change.

## Current state

Mostly stubs. The API services have the template's weatherforecast sample removed; apart from Catalog, Search, Profile and Orders they have no endpoints yet. Email has no endpoints but sends a welcome email when a customer registers. Warehouse has a logistics-styled shell (top header, safety-yellow accents), a floor dashboard with the pick queue, an inventory list with level filters and search, a Receiving page that imports stock from `data/products.json`, and a pick queue of paid orders whose tickets can be completed (dispatched). Picks and imports tell Catalog when a SKU is low or out of stock, and the shop shows it. CatalogManager has a styled back-office shell, a dashboard, a product list with an edit page for description and price, an import from `data/products.json`, and a Publishing page that publishes the catalog and sends `NewCatalogAvailable`. The client is a storefront for browsing and searching the catalog, with sign up, sign in and an account area for delivery addresses and fake payment cards (see Client below), plus a cart and a checkout that places a pending order with Orders. The order then runs through a saga: PaymentGateway takes a mock payment, Orders marks it Paid and sends it to the Warehouse, someone completes the ticket there, Orders marks it Completed, and Email tells the customer it's on its way.

## Local URLs and ports

The .NET apps and the Nuxt dev server run on the host. Caddy runs in Docker and reaches them through `host.docker.internal`. `*.localtest.me` resolves to 127.0.0.1, so no hosts file changes are needed.

| URL | Target |
|---|---|
| `api.localtest.me/catalog/*` | Catalog, ports 5263 and 5264 (round robin) |
| `api.localtest.me/orders/*` | Orders, ports 5053 and 5054 (round robin) |
| `api.localtest.me/search/*` | Search, port 5069 |
| `api.localtest.me/profile/*` | Profile, port 5311 |
| `shop.localtest.me` | Nuxt client, port 3000 |
| `warehouse.localtest.me` | Warehouse MVC app, port 5223 |
| `catalog-manager.localtest.me` | CatalogManager MVC app, port 5003 |
| `seq.localtest.me` | Seq (logs) |
| `mail.localtest.me` | Mailpit (SMTP on 1025) |
| `nats.localtest.me` | NATS dashboard |

PaymentGateway (port 5195) and Email (port 5299) aren't routed through Caddy: nothing outside calls them, they only handle messages from the bus.

The ports come from the `http` profile in each service's `Properties/launchSettings.json`; keep the Caddyfile in sync if they change. Caddy uses `handle_path`, which strips the `/servicename` prefix, so controllers route from `/`. Each app has only an `http` launch profile and no HTTPS redirection or HSTS; Caddy is the only entry point.

The Enterprise MVC apps get their own subdomains rather than path prefixes, so their root-relative links and static assets work without a path base.

Catalog and Orders run two instances each, and the second-instance ports (5264, 5054) exist only in `run.sh`. Caddy round robins across the instances and actively health checks each one's `/health` every 30s, so an instance that's down is skipped. Between checks, a request that fails to connect is retried on another instance (`lb_try_duration 5s`), and the failed instance is skipped for 30s (`fail_duration`). To add an instance, add a line to `APPS` in `run.sh` (with the next `InstanceN` name) and the port to the matching `reverse_proxy` in the Caddyfile.

Infra also includes SQL Server (1433), Postgres (5432) and NATS (4222, monitoring on 8222). Their data lives in `infra/data`, which is gitignored.

## Decisions

- **API gateway through Caddy, one host with path prefixes:** the client sees a single API origin. Services talk through async messaging, which is the point of the demo. The one HTTP call between them is fetching data after a notification: a message says something changed, and the receiver fetches the current state (e.g. CatalogManager's `GET /api/products`) rather than the message carrying it.
- **Controllers rather than minimal APIs** for the services.
- **Autofac and Serilog in every .NET app:** Autofac is the DI container (`AutofacServiceProviderFactory`). Serilog is configured from the `Serilog` section of `appsettings.json`, writes to the console and to Seq (`http://localhost:5341`), and tags each log with an `Application` property. Each app logs every HTTP request (`UseSerilogRequestLogging`).
- **Nuxt in SPA mode (`ssr: false`):** the browser calls the APIs directly, so there's no Node server in the request path. The API base URL is `runtimeConfig.public.apiBase` (`http://api.localtest.me`). `vite.server.allowedHosts` includes `shop.localtest.me` so requests through Caddy aren't rejected. The dev server is bound to `127.0.0.1`, because by default it listens only on IPv6 `::1`, which Caddy can't reach from Docker.
- **Node 22 for the client** (pinned in `src/client/.nvmrc`). Current Nuxt needs Node 20+, and the machine's nvm default is 18, so run `nvm use` first.

## Messaging observability

- Every `BusModule` configures the same bus extras from `src/Shared/Messaging`: `SimpleBackoffDeliveryRetryStrategy` (from Nimbus), `CorrelationIdInterceptor` as a global inbound interceptor and `OutgoingMessageLoggingInterceptor` as a global outbound one. Each `AssemblyScanningTypeProvider` also scans the Shared assembly, or Autofac can't resolve the interceptors.
- `CorrelationIdInterceptor` puts the incoming message's `CorrelationId`, `MessageId` and `ResultOfMessageId` in Nimbus's `CallContext` before a handler runs, and `CorrelationIdEnricher` (added in each `Program.cs` with `.Enrich.With<CorrelationIdEnricher>()`) copies them onto every log written in the handler. Nimbus carries the correlation id onto messages sent from a handler, so filtering Seq by `CorrelationId` shows a whole chain across services (e.g. Profile's `CustomerRegistered` through to Email's `SendEmailCommand`). Messages sent from an HTTP request start a new correlation id.
- `OutgoingMessageLoggingInterceptor` logs every command, event and request sent, with its message id and correlation id.

## CatalogManager data

- `Domain/` holds the entities (`Product`, with `CoffeeDetails` as an owned type mapped to `Coffee*` columns).
- `Data/` holds `IDataContext` and `DataContext` (EF Core, SQL Server). Entity mappings are `IEntityTypeConfiguration` classes in `Data/Mapping`, applied by assembly scan.
- Schema changes are DbUp scripts in `Data/Migration` (embedded resources, run in name order at startup, journal in `dbo.SchemaVersions`). Add a new numbered `.sql` file; don't edit ones that have run. EF migrations aren't used.
- `Infrastructure/DataModule.cs` registers the context with Autofac, per lifetime scope, as `IDataContext`.
- The import (`Import/ProductImporter.cs`) upserts by SKU. New products take the file's price; re-imports keep the existing price. It copies each product's PNG from `data/images/rendered` into `wwwroot/images/products` (gitignored), served by `UseStaticFiles` because `MapStaticAssets` only knows build-time files. The default path is `Settings:ProductImportPath`, relative to the project folder.
- Publishing (`Publishing/CatalogPublisher.cs`) marks every priced product `Published`, records a `CatalogPublication`, saves, then publishes `NewCatalogAvailable` (from `CatalogManager.Messages`) on the bus. Subscribers fetch the products from the API. The API serves the products' current values, so edits to a published product show up there before the next publish.
- `GET /api/products` (`Controllers/Api/PublishedProductsController.cs`) returns the published, priced products with `imageFileName` and an absolute `imageUrl` built from the request host. Its response shapes are in `Models/Api`.

## Warehouse data

- Warehouse uses Postgres (`warehouse` database) with Marten, set up like Catalog: `Domain/StockItem` is the document, with the SKU as its id (set in `Program.cs`), and Marten creates its schema at startup.
- `StockItem` holds only the SKU, name, stock and `WeightGrams` (from `coffee.weightGrams`, so null for equipment). `Domain/StockLevel` derives In stock / Low / Out; low is `StockLevels.LowStockThreshold` (10) units or fewer.
- The import (`Import/StockImporter.cs`, the Receiving page) upserts by SKU. New items take the file's stock; re-imports update the name and weight but keep the existing stock. The default path is `Settings:ProductImportPath`, relative to the project folder.
- Stock alerts (`Domain/StockAlerts`) publish `LowStockWarning` or `OutOfStock` (from `Warehouse.Messages`, SKU only) for an item at those levels. The import sends one for every low or empty SKU, every time. Completing a dispatch reloads the picked SKUs after saving and sends one only for a SKU whose level the pick changed (the level before is the reloaded stock plus the quantity picked), after `OrderProcessed`. Nothing announces a SKU going back in stock; stock only goes up on a new item's first import.
- `Domain/Dispatch` is an order to pick, keyed by order id (optimistic concurrency on). `App/BusHandlers/ProcessNewOrder` handles `OrderConfirmedEvent` as a competing event and inserts a Pending dispatch, ignoring one it already has.
- The Pick queue (`DispatchController`, `/Dispatch`, `?status=Dispatched` for the log) lists dispatches; a ticket shows the pick list against stock on hand and the ship-to label. Complete (`Dispatching/DispatchCompleter`) decrements stock with Marten patches (atomic in the database, so concurrent dispatches don't lose updates; stock isn't checked and can go negative), marks the dispatch Dispatched, saves, then publishes `OrderProcessed`. Completing twice at once hits the concurrency check and shows a flash. There's no outbox, so a failed publish leaves the dispatch done but Orders not told.
- The inventory list filters in memory (`?level=Low|Out`, `?q=` on SKU or name), since there are only a few dozen SKUs.

## Catalog data

- Catalog uses Postgres (`catalog` database) with Marten as a document store. `Domain/Product` is the document, with the SKU as its id (set in `Program.cs`). Marten creates its schema at startup (`ApplyAllDatabaseChangesOnStartup`); there are no migration scripts.
- `Handlers/StoreNewCatalog` handles `NewCatalogAvailable` as a competing event, so one instance handles each publication. It fetches CatalogManager's `GET /api/products` (`Settings:CatalogManagerUrl`), stores every product, deletes products no longer published, downloads each image into `wwwroot/images/products` (gitignored), then publishes `CatalogUpdated` (from `Catalog.Messages`). Both instances run from the project folder, so they share the images.
- `Caching/ProductCache` holds every product in memory. `LoadProductCache` fills it at startup, and `Handlers/RefreshProductCache` reloads it from Marten on `CatalogUpdated`, a multicast event, so every instance refreshes its own copy.
- Stock levels: `Domain/StockStatus` is a separate Marten document per SKU (`Low` or `Out`; no document means in stock), so storing a new catalog doesn't reset it and the warehouse can report SKUs before they're published. `Handlers/RecordStockLevel` stores `LowStockWarning`/`OutOfStock` as competing events; `Handlers/UpdateCachedStockLevel` handles the same events as multicast and sets the level in every instance's cache straight from the message, so it doesn't wait on the database write. `Reload` merges the stored levels over the cached ones.
- `GET /products` serves from the cache, not the database. Each product has a `stockLevel` (`InStock`, `Low`, `Out`, as strings). Image URLs are built from `Settings:PublicBaseUrl` (`http://api.localtest.me/catalog`), because Caddy strips the `/catalog` prefix and the request doesn't carry it.

## Search data

- Search uses Postgres (`search` database) with EF Core (Npgsql) and DbUp, following CatalogManager's layout: `Domain/`, `Data/` (`IDataContext`, `Data/Mapping`), and DbUp scripts in `Data/Migration` run at startup. Tables and columns are lowercase snake_case, so they need no quoting.
- `products` holds only the SKU (primary key) and the text fields. `search_vector` is a generated `tsvector` column with a GIN index, weighted name (A), then category/origin/region (B), tasting notes/process/roast (C), and description (D). EF maps it as the read-only shadow property `SearchVector`.
- `Handlers/IndexNewCatalog` handles `NewCatalogAvailable` as a competing event. It fetches CatalogManager's `/api/products`, then upserts by SKU and deletes products that are no longer published, in a transaction that locks the table so concurrent handlers take turns.
- `GET /products?q=...&limit=20` uses `websearch_to_tsquery('english', q)`, so quoted phrases, `OR` and `-term` work. Results are ranked with `ts_rank`. Keep `EF.Functions.WebSearchToTsQuery` inline in the query, and order before the `Select`, or EF can't translate it.

## Profile data

- Profile uses SQL Server (`Profile` database) with EF Core and DbUp, laid out like CatalogManager: `Domain/` (`Customer`, `DeliveryAddress`, `PaymentCard`), `Data/` (`IDataContext`, `Data/Mapping`), DbUp scripts in `Data/Migration`, and `Infrastructure/DataModule.cs`.
- Auth: `POST /auth/register` and `POST /auth/login` return a JWT plus the account. Passwords are hashed with ASP.NET Core Identity's `PasswordHasher` (no Identity tables). `Auth/TokenIssuer` signs the token with the symmetric key in `Settings:Jwt`, so another service could validate it with the same settings. `MapInboundClaims` is off, so the customer id is the `sub` claim (`User.CustomerId()`).
- `GET/PUT /account`, and `/addresses` and `/cards` (list, create, `POST {id}/default`, delete; addresses also `PUT`) need the bearer token and only touch the caller's rows. Each customer has one default address and one default card: the first one added, whichever is marked default, and the oldest remaining if the default is deleted.
- Registering publishes `CustomerRegistered` (from `Profile.Messages`). Unlike the catalog events it carries the email and name, so Email doesn't need an authenticated call back to Profile.
- Cards are very fake: `Cards/TestCards` lists the only accepted numbers (Stripe-style test cards, also served by `GET /cards/test-numbers`). Only the brand, last four digits and expiry are stored; the CVC is checked for shape and discarded.

## Orders data

- Orders uses SQL Server (`Orders` database) with EF Core and DbUp, laid out like Profile: `Domain/` (`Order` with an owned `OrderAddress` mapped to `Delivery*` columns, `OrderLine`, `Product`), `Data/` (`IDataContext`, `Data/Mapping`), DbUp scripts in `Data/Migration`, and `Infrastructure/DataModule.cs`. Orders runs two instances, so `DatabaseMigrator` takes a SQL Server application lock (`sp_getapplock`) first and the instances take turns.
- Auth: validates Profile's JWT with the same `Settings:Jwt` (issuer, audience, key). `User.CustomerId()` and `User.Email()` read the `sub` and `email` claims.
- `Products` is Orders' own copy of the published catalog's names and prices. `Handlers/UpdatePriceList` handles `NewCatalogAvailable` as a competing event, fetches CatalogManager's `/api/products` and upserts by SKU, deleting unpublished products, under a table lock. Orders are priced from it, never from the shop. It's empty until the next publish after Orders first starts.
- `POST /orders` takes a shop-generated order `id`, SKUs and quantities, and copies of the chosen delivery address and card (brand, last four) as the shop loaded them from Profile; Orders doesn't check them against Profile. It creates a `Pending` order and returns it (201). Posting the same `id` again returns the existing order, so retries don't duplicate. An unknown SKU is a 400 on `Items`. `GET /orders` and `GET /orders/{id}` only return the caller's orders.
- Placing an order publishes `OrderPlaced` (from `Orders.Messages`) with the amount and card, after saving. There's no outbox, so a failed publish leaves the order Pending.
- `Management/OrderManager` runs the order saga (`Pending` → `Paid` → `Completed`). Each step loads the order, applies the event through a method on `Order` (`ApplyPayment`, `Complete`), saves, then publishes the event that starts the next step. If the order is already in the step's target state (a redelivery after the publish failed), it publishes again rather than doing nothing, so subscribers must tolerate repeats. An order in any other state is ignored.
  - `Handlers/RecordPayment` (`PaymentSuccessful`) → `PaymentSucceeded`: sets `Paid`, then publishes `OrderConfirmedEvent` with the customer's name, delivery address and pick list.
  - `Handlers/RecordDispatch` (`OrderProcessed`, from `Warehouse.Messages`) → `Processed`: sets `Completed`, then publishes `OrderCompleted` with the customer's email and name, address, items and total.
- The order keeps the customer's first and last name from the JWT's `given_name`/`family_name` claims at placement, for the events. Orders placed before that have blank names.
- `DatabaseMigrator` releases its app lock explicitly: closing a pooled connection doesn't end the session, so the lock would otherwise outlive the migration and time out the other instance.
- Shipping (`Pricing/Shipping`): free from $60, otherwise $9.95. The client's `shippingFor` in `useCart.ts` mirrors it for display.

## PaymentGateway

- `Handlers/TakePayment` handles `OrderPlaced` as a competing event, charges `Payments/MockCardProcessor`, then publishes `PaymentSuccessful` (from `PaymentGateway.Messages`).
- The processor is deliberately flaky: it keeps an in-memory count of attempts per order (a singleton), throws on the first, and takes 30 seconds on the retry, so Nimbus's backoff redelivers it and the order sits Pending for about 35 seconds. Nothing is declined. It also remembers each order's transaction id, so a redelivery after success doesn't charge twice. A restart forgets all of it.

## Email

- `Handlers/SendWelcomeEmail` handles `CustomerRegistered` as a competing event: it renders the `Welcome` template and sends a `SendEmailCommand` (from `Email.Messages`) back to Email. `Handlers/SendEmail` handles the command and delivers it over SMTP with MailKit (`Sending/SmtpSender`, `Settings:Smtp`, Mailpit on 1025 locally). Anything on the bus can send mail with the command.
- `Handlers/SendDispatchEmail` handles `OrderCompleted` and sends the `OrderDispatched` template (items, total, address, a link to the order) the same way.
- Templates are embedded resources in `Templates/`: `{Name}.txt`, whose first line is `Subject: ...`, and an optional `{Name}.html`. `EmailTemplates.Render` fills `{{Field}}` placeholders (HTML-encoded in the HTML version) and throws on a missing value.

## Client

- Pages in `src/client/app/pages`: home (`index.vue`), `shop.vue` (browse with category, roast, origin and sort filters held in the query string, so filtered views can be linked), `search.vue` (`?q=`), and `products/[sku].vue`.
- `composables/useCatalog.ts` fetches Catalog's `GET /products` once (shared `useFetch` key `catalog`) and everything filters client-side. It also exports `categories`, `roasts`, `categoryLabel` and `formatPrice`, which Nuxt auto-imports.
- Search results come back as ranked SKUs and are joined to the catalog by SKU, so a product Search knows about but Catalog doesn't is skipped.
- Styling is plain CSS: tokens and shared classes in `assets/css/main.css`, component styles scoped. The palette matches the product bag art. Fonts are Fraunces and Inter from Google Fonts.
- Accounts: `composables/useAuth.ts` keeps the JWT and account summary in localStorage (`useAuth`), and `useProfileApi()` is a `$fetch` that sends the token and, on a 401, signs out and redirects to `/login?redirect=`. `plugins/auth.client.ts` refreshes the account on load and drops a dead token. `problemMessages()` turns ProblemDetails validation errors into per-field messages.
- Pages: `login.vue`, `register.vue`, and `account.vue` (the `auth` middleware plus side nav) with children `account/index.vue` (details), `account/addresses.vue` (uses `components/AddressForm.vue`) and `account/cards.vue`.
- Stock: `components/StockBadge.vue` shows Low stock / Out of stock on product cards, the product page and the cart. An out of stock product can't be added to the cart, and `useCart().outOfStock` blocks checkout while the cart holds any. Orders doesn't check stock itself.
- Cart: `composables/useCart.ts` keeps SKUs and quantities in localStorage (`nimbus.cart`) and joins them to the catalog for names and prices; SKUs no longer in the catalog are dropped from view. Pages `cart.vue`, `checkout.vue` (`auth` middleware; picks an address and card from Profile, defaulting to the customer's defaults), `orders/[id].vue` (`?placed=1` shows the thank-you) and `account/orders.vue`.
- `useServiceApi(service)` is the authenticated `$fetch` behind `useProfileApi()` and `useOrdersApi()`. `problemMessages(error, service)` names the service in its fallback message.

## Running

`./run.sh up` / `./run.sh down` / `./run.sh status` starts and stops everything; it's intended for demos without an IDE. To manage the infra and the apps separately, use `infra-up` / `infra-down` (Docker only) and `start` / `stop` / `restart` (apps and client only, leaving the infra alone). `up` is `infra-up` then `start`, and `down` is `stop` then `infra-down`. `up` starts the Docker infra (restarting Caddy to pick up Caddyfile changes), builds the solution, runs each .NET app instance from its `bin/Debug/net9.0` executable with `ASPNETCORE_URLS` set to its port, and starts the Nuxt dev server under Node 22 via nvm. It waits for each app to respond before printing the URLs. PIDs and logs are in `.run/` (gitignored). Each app runs in its own process group, and `down` stops apps by those PIDs. Never stop processes with a broad `pkill -f` pattern: `Services/` matches macOS system processes. `down` also runs `docker compose down`; data persists in `infra/data`.

`./run.sh reset` resets the demo: it stops the apps, empties every database with `scripts/clear-postgres-data.sql` and `scripts/clear-sqlserver-data.sql`, deletes the copied product images, then starts the apps again. The scripts empty every table but keep the schemas and DbUp's `SchemaVersions` journal, so migrations don't re-run. They find the tables themselves, so new tables are covered, but a new database needs adding to its script. The infra must be up.

Each app instance gets an `Instance` environment variable (`Instance1`, `Instance2`, ...) from the last field of its `APPS` line in `run.sh`. Single-instance apps are always `Instance1`. The apps read it through configuration (`Configuration["Instance"]`); `appsettings.json` defaults it to `Instance1` for IDE runs. Serilog adds it as an `Instance` property on every log, alongside `Application`, so you can tell instances apart in Seq.

Running one app by hand: `dotnet run --project src/Services/<Name>` (uses the `http` launch profile port).
